Principles

Selected Fluent and Windows principles that could help shape motion in VS Code.

Useful motion

Purpose first

Use motion to explain a change, guide the next step, or confirm an outcome.

Reflect state

Start and stop with the real operation. Never imply unverified progress.

Lead signal

Choose the indicator closest to the work and suppress repeated status motion.

Preserve meaning

Keep every state clear through text, icons, and accessible feedback.

Shared patterns

Use the same motion for equivalent states across VS Code.

User control

Let new input interrupt, skip, or reverse motion immediately.

Natural timing

Match duration and easing to the element’s size and travel distance.

Preserve context

Connect before and after states so people can follow what changed.

Show hierarchy

Distinguish top-level, deeper, and sibling navigation through movement.

Intentional delight

Immediate results

Let delight accompany success without blocking the outcome or next action.

Focused delight

Animate only the element tied to the moment, not the surrounding UI.

Meaningful moments

Celebrate significant achievements or transformations—not routine actions.

Product character

Use signature motion, like VS Code Pet, to express personality and mark completion.

These principles provide a framework for addressing the issues documented in Findings.

Result: Both animations consistently added CPU overhead in this waiting-for-an-answer state and meet this audit's High threshold. The shimmer added more renderer CPU overhead than the logo when measured separately.

How and where we tested
  • Build and device: VS Code Insiders 1.144.0-insider, commit c797482ce0d1bc89497a5636b69da98493e54036, macOS arm64. The device stayed on battery with the same power mode throughout.
  • Environment: A separate Agents Window using an isolated profile and a scratch workspace. Installed extensions were disabled using --disable-extensions, and the product's disabled-extensions notice was verified. Built-in product services remained available.
  • Scenario: A real multiple-choice question was left unanswered, keeping the working logo and thinking-text shimmer visible. No terminal command or active model generation was part of the measured waiting state. The user paused work during measurement.
  • Comparison: Seven on/off pairs for each case, with 10 seconds per condition. Order alternated between on/off and off/on. The baseline kept both animations static; individual tests enabled only the target animation. All three cases took approximately eight minutes in total.
  • Controls: The original production sprite-atlas logo was paused or played. The original shimmer's JavaScript timeline updates were stopped and resumed independently. Timeline movement, shimmer-driver writes, unchanged request content and window size were checked during each sample. Original animation playback was restored afterward.
  • Calculation: For each pair, subtract baseline CPU from active CPU. The headline is the median of those seven paired differences; the range is the smallest to largest difference, not a confidence interval. Both-on cost was measured separately, not calculated by adding the individual results.
  • Rating: High means every pair added at least 5 CPU percentage points; Moderate means every pair added at least 1; Low means every difference was strictly between -1 and +1. These are this audit's prioritization thresholds, not universal performance budgets.

Scope: CPU pp means extra renderer CPU in percentage points; 100% corresponds to one fully used CPU core, not the whole device. GPU-process and browser-process CPU are recorded separately in the raw data and are not included above. These results do not mean the product became that percentage slower. They apply to this build, device, window size and waiting state; background OS activity and instrumentation remain limitations.

When to use motion Motion requirements Supporting evidence

When to use motion

For functional motion, ask "Would motion communicate feedback, state changes, or the next action more clearly than a static presentation?" If yes, use restrained motion and preserve the same information when Reduced Motion is enabled; if no, use a static presentation.

Decorative and expressive motion are outside the scope of this guideline.

Motion requirements

  • Respond immediately to input: Confirm the action with a clear state change. Add motion only when it makes the feedback easier to understand.
  • Show when input is needed: Stop active-work motion when a user response is required. Use a stable icon, a clear label such as "Input needed", and the available action. Do not loop while waiting.
  • Keep feedback local: Keep controls, hit targets, labels, and surrounding layout stable. Do not block input or duplicate a signal for the same operation.
  • Do not manufacture waiting: A context-tested indicator delay can avoid flashes during short operations; never delay acknowledgment, results, or the next action to show an animation.
  • Preserve meaning without motion: Honor the resolved workbench Reduced Motion preference, including changes during playback. Use recognizable static glyphs, readable status, available actions, and meaningful measured updates, not slower decorative loops.
  • Budget CPU as well as attention: Stop with the operation, pause when hidden or offscreen, and dispose animation work when removed. Measure CPU cost alongside clarity and accessibility before standardizing a pattern.
  • Validate real states: Check rapid input, interruption, failure, cancellation, simultaneous activity, keyboard and screen-reader feedback, and preference changes before standardizing values. Never make paused work look active or rely on per-frame announcements.

Timing verification

  • Component-specific cycles: The local Explorer comparison did not support one 1,500 ms cycle for rotation, grid, and ring. Duration-only changes altered dot phases; proportional delay changes preserved phases but remain a design proposal.
  • Completion is not one short cue: The 400 × 400 px generated-image fixture revealed in approximately 3.6 seconds. Its sequence depends on reveal geometry and pacing, not a 120–200 ms ease-out. Reduced Motion skipped the reveal and kept the image visible.
  • Progress has separate clocks: Source uses 100 ms linear width interpolation between measured updates, a 4-second indeterminate bar cycle, and a 10-second Undo deadline. Countdown hover pause and resume were verified; interpolation is not the task duration.
  • Lifecycle remains a requirement: The grid paused offscreen; the ring's pause class was applied but its animation kept running in the local CSS-variant probe. Both dot variants became static with the browser's Reduced Motion preference. The ring needs implementation follow-up.

Local source and Component Explorer checks, not installed-product or user validation. No shared acknowledgment, entrance, completion, or emphasis duration is established. Verification data and source hashes.

    Accessibility

    Principles VS Code guidelines Reduced-motion alternatives Review checklist Standards and sources

    Principles

    1. Preserve meaning without motion

      Working, needs input, paused, completed, and failed must remain distinguishable through stable labels and icons. Turning animation off must not make an active task look stopped.

    2. Protect reading and concentration

      Keep the editor, conversation, and focused controls stable. Background work should not continually compete with the task a person is reading or editing.

    3. Keep control with the user

      Let people reduce animation without cancelling work, losing updates, or giving up access to actions. Motion preferences and screen-reader support are separate needs; test both.

    VS Code guidelines

    1. Honor the resolved reduced-motion preference

      Use workbench.reduceMotion: auto follows the OS preference, on reduces motion, and off explicitly opts out. Web prototypes follow prefers-reduced-motion. Apply changes while the interface is running, not only at startup. Remove nonessential traveling borders, shimmer, rotation, zoom, and sliding effects rather than merely slowing them down.

    2. Make every state understandable without animation

      Pair recognizable icons with clear labels such as Working, Needs approval, Completed, or Failed. Do not rely on movement or color alone. Keep real progress values and available actions; a frozen spinner by itself can look like a stalled operation.

    3. Provide control over persistent motion

      Let users disable, stop, or hide nonessential ongoing animation without stopping the agent, terminal command, or download. A discoverable motion setting can provide this control; each spinner does not need its own pause button. Do not assume every loading animation qualifies as essential.

    4. Keep text, focus, and the viewport stable

      Use readable status text instead of animating the words people need to read. Do not move a focused control, steal focus for progress updates, or force chat back to the newest output after someone scrolls away. Provide a clear return-to-latest action. Preserve necessary keyboard focus changes when opening or closing a dialog.

    5. Coordinate motion by task and scope

      Prefer one primary animated cue for the same activity within a visible task area. Avoid combining a working logo, text shimmer, animated input border, and spinner to repeat the same message. Keep local feedback for genuinely separate tool work, and use quiet, preferably static, status for background sessions. This is a proposed design rule, not a WCAG limit on the number of animations.

    6. Avoid flashing and abrupt visual effects

      Do not introduce strobing or rapid high-contrast pulsing. Review concurrent indicators together, including across split chats and the Sessions list. Prefer no flashing; any flashing that remains must meet the WCAG flash thresholds, regardless of whether reduced motion is enabled.

    7. Expose meaningful status changes to assistive technology

      Use the existing VS Code accessibility announcement mechanisms for meaningful changes such as Working, Needs approval, and Completed, without taking keyboard focus. Give web status messages appropriate semantics. Avoid announcing every spinner cycle, streamed token, or countdown tick; verify that multiple sessions do not create repeated or competing announcements.

    8. Keep recovery available beyond a short countdown

      For bulk Mark as Done and similar Undo notifications, provide an equivalent persistent recovery route or a compliant way to turn off, adjust, or extend the time limit, unless a documented exception applies. Make recovery keyboard accessible. Removing the countdown animation does not remove the time barrier.

    Review checklist

    Before approving a motion pattern, define its purpose, its no-motion alternative, and how it behaves alongside other activity.

    • Preferences: Test OS reduced motion with auto, explicit on and off, and preference changes while tasks are running. Check CSS, SVG, JavaScript, and embedded surfaces where used.
    • State parity: Verify working, needs input, paused, cancelled, completed, and failed states with motion enabled and reduced. Do not hide progress or available actions.
    • Concurrent activity: Review a realistic screen with multiple sessions, split chats, and a running tool. Evaluate combined distraction and flashing, not only isolated components.
    • Keyboard and reading: Navigate controls, scroll back through a streaming response, and open or close panels. Verify focus and reading position remain predictable.
    • Screen readers: Check meaningful announcements, labels, and recovery actions. Avoid repeated announcements and unnecessary interruptions.
    • Themes and zoom: Check dark, light, and high-contrast themes and enlarged UI. Labels and essential status graphics must remain readable, distinguishable, and unclipped.
    • Timing and control: Check long-running indicators and Undo expiry. Verify disabling decorative motion does not cancel work, and recovery remains usable.

    Standards and sources

    Use WCAG 2.2 as a reference for accessibility review, with applicability assessed for each product surface. The guidelines above also include stricter proposed design choices.

    • Pause, Stop, Hide - 2.2.2, Level A: Automatically starting movement lasting more than five seconds alongside other content needs a pause, stop, or hide mechanism unless essential. Auto-updating information has a related requirement without the five-second exception. This is not a rule to stop every task indicator at five seconds. Read the criterion.
    • Animation from Interactions - 2.3.3, Level AAA: Nonessential motion animation triggered by interaction can be disabled. Proposed here as a product baseline beyond AA. Read the criterion.
    • Three Flashes or Below Threshold - 2.3.1, Level A: No more than three flashes in any one-second period, unless below the defined general and red flash thresholds. Our proposed design policy is to avoid flashing altogether. Read the criterion.
    • Status Messages - 4.1.3, Level AA: Applicable status messages are programmatically available to assistive technology without receiving focus. Read the criterion.
    • Timing Adjustable - 2.2.1, Level A: Content-imposed time limits need a way to turn off, adjust, or extend them unless a specified exception applies. Review whether an equivalent persistent recovery route removes the time-limited action. Read the criterion.
    • VS Code accessibility: Use existing accessibility settings, keyboard navigation, Accessible View, and configurable accessibility signals rather than introducing competing feedback systems. VS Code accessibility documentation.
