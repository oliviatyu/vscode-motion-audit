Principles

Selected Fluent and Windows principles that could help shape motion in VS Code.

Useful motion

Purpose first

Use motion to explain a change, guide the next step, or confirm an outcome.

Reflect state

Start and stop with the real operation. Never imply unverified progress.

Lead signal

Choose the indicator closest to the work and suppress repeated status motion.

Preserve meaning

Keep every state clear through text, icons, and accessible feedback.

Shared patterns

Use the same motion for equivalent states across VS Code.

User control

Let new input interrupt, skip, or reverse motion immediately.

Natural timing

Match duration and easing to the element’s size and travel distance.

Preserve context

Connect before and after states so people can follow what changed.

Show hierarchy

Distinguish top-level, deeper, and sibling navigation through movement.

Intentional delight

Immediate results

Let delight accompany success without blocking the outcome or next action.

Focused delight

Animate only the element tied to the moment, not the surrounding UI.

Meaningful moments

Celebrate significant achievements or transformations—not routine actions.

Product character

Use signature motion, like VS Code Pet, to express personality and mark completion.

These principles provide a framework for addressing the issues documented in Findings.

Proposed guidance

Component motion

Proposed component-level motion guidance for VS Code. Choose a role based on what the interface needs to communicate, then apply its behavior, timing, and easing consistently.

Principles Choose a motion role Shared guidelines Supporting evidence

Direction for review. These roles and values are starting points for prototyping and team review, not approved motion tokens.

For feedback within a component: acknowledgment, progress, attention, completion, time remaining, and emphasis. Use Interface transitions for relationships between surfaces and Animated icons for glyph-level behavior.

Principles

  1. Choose by meaning

    Distinguish work in progress, a request for input, and a confirmed outcome. Select the role that explains the actual state rather than the most noticeable effect.

  2. Let the operation set the pace

    Measured progress and countdowns follow real values. Feedback starts promptly, stops when its state ends, and never delays the result or the next action.

  3. Keep emphasis proportional

    Use one primary progress signal per scope. Reserve added emphasis for meaningful moments, and preserve the same information without motion.

Choose a motion role

Choose the feedback role first, then use its behavior and constraints to evaluate a prototype. Timings and easing below are proposals, not measured product specifications.

Proposed component motion guidelines for VS Code
Motion roleUse whenBehaviorTimingEasingConstraints

Shared guidelines

  • Behavior: Bind the treatment to the real component state. Preserve separate paused, failed, cancelled, and completed outcomes; do not invent progress.
  • Constraints: Keep feedback local. Do not move unrelated content, block input, or layer multiple signals for the same scope.
  • Reduced Motion: Honor the resolved workbench preference. Remove optional interpolation and repeating decoration while keeping state labels and meaningful measured updates.
  • Validation: Check rapid input, interruption, failure, cancellation, simultaneous activity, keyboard and screen-reader feedback, and preference changes in the live product before standardizing values.
Supporting evidence

The current audit documents overlapping progress signals, needs-input treatments, generated-image completion, and a real undo countdown. Those cases motivate state-based roles and scoped feedback; they do not validate the proposed timing ranges or prove that every role needs animation.

  • Findings: existing component observations and product recordings.
  • Coordination: simultaneous activity across session, response, tool, and field scopes.
  • Current motion: recordings and component states to compare against a proposal.

The audit is the research base, not an approval of these roles or values. Some directions need further live validation and user testing.

Proposed guidance

Interface transitions

Help people follow what changes without losing their place in the workspace.

Principles Choose a transition pattern Shared guidelines Supporting evidence

Direction for review. Seven proposed patterns informed by live observations and existing audit evidence. Schematics and prototype values are not current product specifications.

For changes between content, details, surfaces, and layouts. Use Component motion for feedback roles and Animated icons for motion inside individual glyphs.

Principles

  1. Start with no animation

    Animate only when the change needs explanation. Keep rapid, repeated, and already-clear changes immediate; never delay input or results.

  2. Preserve the workspace relationship

    Keep the surrounding editor stable. Connect a changed surface to its origin without moving the whole workbench or implying an unintended hierarchy.

  3. Keep context and control

    Preserve selection and reading position. Let new input interrupt, and retain state, labels, and the appropriate focus behavior when motion is off.

Choose a transition pattern

Choose by the relationship that changes. Each pattern separates the recommendation, prototype values, and supporting observations.

Shared guidelines

VS Code uses workbench.reduceMotion; web demos follow prefers-reduced-motion. Demos are manual and keep focus on their controls.

Supporting evidence

Live audit: Insiders 1.143.0, build 341e0fa, macOS, October 19, 2026. Tested 18 actions with Reduced Motion off and on in an isolated profile. Agent handoffs remain unverified. Each pattern's supporting details distinguish observed behavior from the proposal; documentation links establish interactions, not proposed motion.

For the measured view, folder, Panel, Quick Open, side-bar, split, tab, and definition-navigation actions, no surface transition was detected. The Find widget used a 200 ms linear transform, suppressed with Reduced Motion. This does not mean those actions have zero processing latency.

Chat disclosure and selection, state handoffs, Panel maximization, typing, and drag-resizing were not measured in this run. The proposals and their examples are not claims of live validation for those cases.

Proposed guidance

Animated icons

Give every moving icon a clear job. Show where work is happening, distinguish a request for attention, and preserve meaning when motion is off.

Principles Choose a motion role Shared guidelines Supporting evidence

Direction for review. Recommendations grounded in current product and Component Explorer research. The shared timing baseline is a proposal to test, not a shipped standard.

For motion within individual icons, not layout transitions, text shimmer, composer borders, or large progress surfaces.

Principles

  1. Make the state clear

    Distinguish ongoing work, input needed, and outcomes through recognizable glyphs and labels. Motion alone is not a status.

  2. Coordinate by purpose

    Choose one primary indicator per operation; retain local feedback for distinct work. Test a shared rhythm for comparable activity loops, not every animation.

  3. Preserve meaning without motion

    Keep status and available actions understandable when animation is off. Never make a paused operation look like work is continuing.

Choose a motion role

Choose by what the user needs to understand. These are proposed roles, not existing component families.

01 / Work is continuing

Indeterminate activity

Use when
Work is active and its completion time is unknown.
Behavior
Loop beside the operation's label, only while it runs. Loop speed must not imply a completion percentage.
Why this direction

The working logo and local tool PixelSpinner already show unknown-duration activity at different scopes. PR fields and submission use separate loading states. This supports operation-bound feedback, not a universal spinner for every wait.

Working-logo evidence · Local-activity evidence · Field and connection evidence

02 / A person needs to act

Attention needed

Use when
Work is paused for approval, input, or another decision.
Behavior
Show a stable attention glyph and “Input needed” label. Do not keep a loading loop running while waiting.
Why this direction

Current session and subagent implementations distinguish running grid from waiting ring, but the ring is also used for loading elsewhere. Existing input-needed product captures show competing icon and row signals. A non-looping waiting state is a proposed change, not a claim about today's behavior.

Current state semantics · Input-needed product cases in Opportunities

03 / A live signal is changing

Live input / output feedback

Use when
Genuine listening or speaking benefits from visible signal feedback.
Behavior
Follow the real signal within the glyph. Keep connecting and idle distinct from capture; validate with live audio.
Why this direction — needs live validation

Voice source separates connecting, idle, listening, and speaking, with audio-reactive bars and a CSS fallback. Reviewed listening/speaking fixtures were static. This role is grounded in that implementation but needs a live audio check before choosing a waveform or rhythm.

Voice observations and verification gap

Show completion, failure, and cancellation as stable outcomes. Use measured progress, not a decorative loop, when a real value is available.

Comparison and implementation checklist · Current grid / ring baselines

  • Keep motion local: Animate within a stable icon slot. Keep the control, hit target, label, and surrounding layout still.
  • Stop with the operation: Show new states immediately, without waiting for a cycle to finish. Pause when hidden and dispose animation work when removed.
  • Honor Reduced Motion: Replace optional motion with a recognizable static glyph and explicit status, not a slower loop. Respond to preference changes during playback.
Supporting evidence

The observations support these proposals, not a validated redesign. Review simultaneous activity in Coordination and the supporting Findings. Repeated indicators suggest a coordination question, not proven user confusion.

Comparison and implementation checklist
  • Compare rhythms: Test the proposed 1,500 ms cycle against the current 1,200 ms ring and 1,820 ms grid, alongside Codicon and the 2,667 ms logo. Compare perceived speed, clarity, distraction, and loop boundaries individually and together at real icon sizes in the editor. Document justified exceptions.
  • Specify the mechanism: Reuse an appropriate component. Record animated properties, ranges, transform origin, cycle or cue duration, repeat count, easing / keyframes, delays, and holds. Mark observed versus proposed values; for live feedback, document signal mapping, update rate, smoothing, and idle thresholds instead.
  • Test interruption: Exercise rapid start / stop, replacement, failure, cancellation, hiding, removal, and becoming visible again. Cancel stale callbacks; do not replay old states or restart a one-time cue on focus or re-render.
  • Verify accessibility: Test state recognition, keyboard use, and screen-reader feedback without per-frame announcements. Check browser preference, workbench setting, and changes during playback separately; fixture overrides do not validate the live setting. See the motion-policy checks and limits.
  • Validate live signals: Test genuine listening / speaking, connecting, idle, and failure. Smoothing must not mask meaningful changes or imply idle capture. Static voice fixtures do not establish responsiveness or user comprehension.

Implementation

Meaning in context

Motion policy
